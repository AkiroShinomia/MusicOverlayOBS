# MusicOverlayOBS 2.1 — архитектура и план развития

Статус: рабочий комплект архитектурных документов.

Дата базового аудита: 2026-08-31.

Цель комплекта — сделать разработку версии 2.1 управляемой: сначала сохранить текущее поведение, затем разделить монолит, убрать дублирование моделей и только после этого расширять редактор.

## Для кого эти документы

- Владелец продукта использует `00-product-and-scope.md`, roadmap и критерии приёмки. Для понимания этих файлов не нужны знания программирования.
- Архитектор использует AS-IS, целевую архитектуру и ADR для принятия технических решений.
- Разработчик начинает этап только после чтения соответствующего ТЗ в `specs/` и связанных ADR.
- Тестировщик использует критерии выхода из этапа и матрицу требований.

## Порядок приоритета

Если документы противоречат друг другу, действует следующий порядок:

1. Явно подтверждённое продуктовое решение владельца продукта.
2. Принятый ADR.
3. ТЗ конкретного этапа.
4. Целевая архитектура и контракты.
5. Roadmap.
6. AS-IS-аудит, который описывает прошлое и текущее состояние, но не задаёт будущее.

Противоречие нельзя молча трактовать в пользу удобства реализации. Его нужно записать в `07-open-questions.md` или оформить новым ADR.

## Уже принятые решения

- Источником истины остаётся общий Git-репозиторий. `Project/` не становится отдельным Git-root: активный код 2.1 должен отслеживаться как часть общего репозитория. Оставлять ли его в этой подпапке или позднее переносить — техническое решение Gate 0, не влияющее на продукт.
- Версия 2.1 — прежде всего безопасный рефакторинг 2.0.1 и фундамент для дальнейшего развития, а не попытка сразу сделать полный аналог After Effects.
- Координаты X/Y означают положение объекта на холсте. Для совместимости они хранят положение его левого верхнего угла в координатах родителя. Anchor используется как точка вращения и масштабирования и не меняет смысл X/Y.
- Тема — самостоятельный готовый снимок всей композиции. Пользователь может открыть встроенную тему, изменить её и сохранить отдельную пользовательскую копию.
- Published хранит только актуальную применённую сцену. История Published не является требованием 2.1. Глобальные настройки сохраняются отдельно от публикации сцены.
- Вложение одной целой композиции в другую (`compositionRef`) не входит в 2.1. Архитектура не должна мешать добавить это позднее, но преждевременный формат в файлах не резервируется.
- OBS показывает обычную веб-страницу, но внутри использует встроенный браузер. Поэтому совместимость JavaScript и CSS всё равно проверяется. До подтверждения матрицы OBS применяется консервативная схема без сборщика и без обязательной зависимости от native ES modules.

## Короткий словарь

- **Scene / композиция** — всё содержимое одного overlay: группы, объекты, расположение, внешний вид, время и анимации.
- **Draft / черновик** — изменения, которые видны в редакторе, но ещё не применены в OBS.
- **Published / применённая сцена** — последняя версия, которую должен показывать OBS.
- **Renderer / рендерер** — механизм, который превращает описание Scene в видимую веб-страницу.
- **Host** — окружение вокруг общего рендерера. PreviewHost добавляет инструменты редактора; ObsHost подключает реальные данные о музыке и звук.
- **Registry / реестр компонентов** — единый каталог доступных типов объектов, их настроек и способа отображения.
- **ADR** — короткая запись важного технического решения, причин и последствий.
- **Контракт** — согласованный формат данных или правило взаимодействия частей программы.

## Правило изменения документации

Каждый этап разработки обязан:

1. сослаться на своё ТЗ;
2. обновить статус требований;
3. записать новое архитектурное решение, если реализация меняет принятый подход;
4. приложить результаты автоматических и ручных проверок;
5. не объявляться завершённым, пока не выполнен его exit gate.
